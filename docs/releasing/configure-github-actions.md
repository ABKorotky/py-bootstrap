# Configure GitHub Actions for releases

Covers the repository changes and GitHub settings the `release` workflow needs.
Do [configure-pypi.md](configure-pypi.md) as well - the two are independent halves
of the same setup.

Files this adds to the repo:

| Path                                   | Purpose                                             |
| -------------------------------------- | -------------------------------------------------- |
| `.github/workflows/release.yml`        | the pipeline                                        |
| `tools/check_release_version.py`       | tag == CHANGELOG == setuptools-scm gate             |
| `tools/smoke_test.py`                  | exercises the installed wheel                       |
| `tools/render_changelog_section.py`    | turns a CHANGELOG section into GitHub release notes |

---

## 1. Repository prerequisites

### 1a. Version from setuptools-scm (done)

`pyproject.toml` already carries this:

```toml
[build-system]
requires = ["setuptools", "setuptools-scm>=8"]

[project]
dynamic = ["version"]      # no static `version =`
dependencies = []          # the tool has no runtime dependencies

[tool.setuptools_scm]      # empty table; no version file written
```

On a tagged commit setuptools-scm yields exactly `0.10.0`; on any later commit it
yields `0.10.1.dev<N>+g<sha>`, so a clean release number can only come from a tag.
setuptools-scm accepts both `v0.10.0` and bare `0.10.0` tags - the workflow and
`tools/check_release_version.py` expect the **`v`-prefixed** form.

### 1b. Root `__init__.py` cleaned (done)

`py_bootstrap/__init__.py` no longer defines `NAME` / `TITLE` / `DESCRIPTION` /
`VERSION` / `AUTHOR` / `AUTHOR_EMAIL` (all duplicated `pyproject.toml`). Only
`PY_VERSION` stays - it is a functional default for generated projects, not
packaging metadata. `docs/conf.py` now reads the version from installed metadata,
and the `tests/test_package.py` canary was removed. Anything else that needs the
metadata at runtime should use:

```python
from importlib.metadata import metadata, version

__version__ = version("ak-py-bootstrap")
_meta = metadata("ak-py-bootstrap")
```

### 1c. CHANGELOG.md is generated by towncrier (done)

`CHANGELOG.md` now carries a `<!-- towncrier release notes start -->` marker and
no `## [Unreleased]` section. Unreleased changes are news fragments in
`changelog.d/`; `make cl-build VERSION=X.Y.Z` folds them into a `## [X.Y.Z]`
section. `tools/check_release_version.py` and `render_changelog_section.py` read
that newest `## [X.Y.Z]` heading. Full workflow: [changelog.md](changelog.md).

### 1d. Dependency groups (done)

Dev tooling is declared as PEP 735 `[dependency-groups]` in `pyproject.toml`
(`test`, `format`, `cs`, `ann`, `doc`, `changelog`, `scm`, `dist`, `release`,
`dev`). Each `make` target installs the group it needs on demand;
`pip install -e . --group dev` sets up a full dev environment. There are no
`requirements*.txt` files.

## 2. Create the `pypi` environment (protected)

Repo **Settings -> Environments -> New environment -> `pypi`**:

* **Required reviewers**: add yourself. The `publish-pypi` job then pauses for a
  manual approval click before it can upload. A malicious PR or a stray branch
  cannot reach PyPI on its own.
* **Deployment branches and tags**: choose *Selected* -> add a **tag** rule `v*`
  (a tag rule, not a branch rule, so releases from `release/<major>.<minor>`
  branches also pass).
* **Secrets**: none. Trusted Publishing needs no secret.

---

## 3. Create the `testpypi` environment

**Settings -> Environments -> New environment -> `testpypi`**:

* Required reviewers: optional (it is only the sandbox).
* Deployment branches and tags: *All* is fine, or restrict to `main`.
* Secrets: none.

---

## 4. Restrict who can push release tags

**Settings -> Rules -> Rulesets -> New ruleset**:

* Target: **Tags**, pattern `v*`.
* Enable **Restrict creations** and **Restrict updates**; bypass list = repo
  admins / maintainers only.

Now only maintainers can start a release, and the `check-version` job double-checks
the tagged commit is reachable from `main` or a `release/*` branch (so patch
releases of older minors can be cut from `release/<major>.<minor>`).

---

## 5. Workflow token permissions

**Settings -> Actions -> General -> Workflow permissions**: leave at
**Read repository contents permission** (the restrictive default). `release.yml`
requests exactly what each job needs and nothing more:

| Job              | Extra permission   | Why                              |
| ---------------- | ------------------ | -------------------------------- |
| `publish-pypi`   | `id-token: write`  | OIDC token for Trusted Publishing|
| `publish-testpypi` | `id-token: write`| same, for TestPyPI               |
| `github-release` | `contents: write`  | create the GitHub Release        |

No other change needed here.

## 6. Smoke-test the pipeline (no real release)

1. **Actions -> release -> Run workflow**, branch `main`, leave `ref` = `main`.
2. `build` and `test-wheel` run; `publish-testpypi` uploads a dev version to
   TestPyPI. `check-version` / `publish-pypi` are skipped (not a tag push).
3. Confirm the new version at
   <https://test.pypi.org/project/ak-py-bootstrap/>.

Re-run freely - `skip-existing: true` on the TestPyPI job tolerates repeats.

## 7. Cut a real release

All release steps are `make` targets (the CI jobs call the same ones), so the
flow is identical on any machine.

```bash
make cl-preview VERSION=0.10.0       # read the section the fragments will produce
make release VERSION=0.10.0          # cut-tag + dist-build + dist-upload
git push origin main --follow-tags
```

`make release` uploads to the real PyPI by default; pass `PYPI=testpypi` to rehearse.

Individual targets, if you'd rather run them by hand:

| Target | Does |
| --- | --- |
| `make cl-preview VERSION=X.Y.Z` | preview the collated `changelog.d/` section |
| `make cl-build VERSION=X.Y.Z` | collate `changelog.d/` into `CHANGELOG.md` |
| `make cut-tag VERSION=X.Y.Z` | verify, collate, commit `Prepare X.Y.Z version`, tag `vX.Y.Z` |
| `make dist-build` | sdist + wheel from a clean tree, then check the wheel installs |
| `make dist-upload` | `twine check --strict` then upload `DIST` to `PYPI` |
| `make release VERSION=X.Y.Z` | `cut-tag` + `dist-build` + `dist-upload` |

To rebuild a released version, check out its tag and run
`make dist-build dist-upload`.

```{note}
Release candidates are not supported by the current flow. `cut-tag` collates the
changelog under whatever version it is given, so `0.10.0rc1` would write a
`## [0.10.0rc1]` section and consume the fragments, leaving nothing for the
final `0.10.0`.
```

What each tag triggers in CI:

| Tag           | `check-version` | PyPI upload            | GitHub Release      |
| ------------- | --------------- | ---------------------- | ------------------- |
| `v0.10.0rc1`  | yes             | `0.10.0rc1` (pre)      | marked *pre-release*|
| `v0.10.0`     | yes             | `0.10.0`               | normal release      |

### CI reuses these targets

```{warning}
The workflows have not been migrated yet. `release.yml` still calls
`tox -e release-check`, `tox -e build` and `tox -e smoke --installpkg dist/*.whl`,
and `changelog.yml` still calls `tox -e cl-check` - envs that no longer exist now
that `tox.ini` is reduced to the interpreter matrix. **CI fails until they are
converted to the `make` targets above.**
```

Once converted, the workflows will only add GitHub-specific plumbing on top of
the same targets a developer runs locally: checkout depth, passing `dist/`
between jobs as an artifact, the protected environments, the OIDC
`pypa/gh-action-pypi-publish` step, and the GitHub Release. Those cannot move
into `make` - everything else is a shared target.

## 8. If something goes wrong

* **`check-version` fails** - tag and CHANGELOG or setuptools-scm disagree.
  Delete the tag (`git push --delete origin v0.10.0`), fix, re-tag. Nothing was
  published.
* **`publish-pypi` fails after upload succeeded partially** - a version is
  already live and immutable. Bump to `v0.10.1` and release that; optionally
  `yank` the bad one on PyPI (hidden from new resolves, still installable by
  exact pin).
* **Wrong artifact published** - you cannot overwrite it. Yank it and release a
  new version.
